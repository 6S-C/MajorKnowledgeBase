# W3｜第 4–5 章《工具与代码元能力》

## 核心笔记

### 1. 工具不是“给模型接一个 API”，而是 Agent 与外部世界之间的受控接口

语言模型只能根据上下文生成下一段内容。Agent 要读取文件、搜索信息、修改代码或调用其他系统，必须把这些能力包装成模型能够选择、运行时能够约束、结果能够回传的工具。

~~~text
用户目标
   ↓
LLM 判断下一步动作
   ↓ 输出工具名与结构化参数
Agent Runtime 校验权限、参数和风险
   ↓
工具在外部环境中执行
   ↓ 返回 stdout / stderr / 状态 / 产物路径
LLM 根据真实结果继续决策或停止
~~~

因此，工具系统至少包含三层：模型负责决策，运行时负责治理，工具负责改变外部状态。工具报错也是环境观察，应该回到下一轮上下文，而不是被包装成“已经完成”。

对 BCI Agent 而言，读取 EEG 文件、执行预处理、汇总指标和提交计算任务都属于工具能力。真正重要的不只是“能调用”，还包括输入数据来自哪里、在哪个环境运行、写了哪些文件、退出码是什么，以及结果能否被独立复核。

### 2. 五类工具按“谁发起、作用于什么”区分

| 工具类型 | 调用方向 | 主要作用 | 设计重点 | BCI 场景示例 |
| --- | --- | --- | --- | --- |
| 感知工具 | Agent 主动调用 | 获取信息 | 限制返回量，保留来源 | 读取数据说明、检索论文、查看训练日志 |
| 执行工具 | Agent 主动调用 | 改变世界 | 权限、隔离、确认、回滚 | 运行预处理、写配置、启动训练 |
| 协作工具 | Agent 主动调用 | 驱动其他 Agent 或人 | 任务边界、交接信息、状态同步 | 把数据检查和论文检索分给不同子任务 |
| 用户沟通工具 | Agent 主动调用 | 向用户传递信息 | 渠道、时机、隐私和重复发送 | 实验完成通知、异常告警、审批请求 |
| 事件触发工具 | Agent 注册、外部触发 | 唤醒 Agent 开始行动 | 幂等、重试、去重和超时 | GPU 任务结束后自动整理结果 |

感知工具主要担心上下文爆炸；执行工具主要担心不可逆副作用；协作工具主要担心任务边界和信息丢失。用户沟通与事件触发还依赖异步运行时，不能简单理解成一次函数调用。

### 3. 专用工具、通用执行器和 Skill 是三种不同的能力表达方式

同一项能力可以做成结构化工具，也可以交给通用终端或代码解释器完成，还可以写成按需读取的 Skill。它们不是简单的替代关系。

| 形态 | 优点 | 主要风险或代价 | 更合适的情况 |
| --- | --- | --- | --- |
| 专用工具 | 参数受 schema 约束，权限和审计粒度清楚，容易测试 | 每个 schema 都占上下文，工具多时选择负担上升 | 高风险、高频、参数复杂、需要精细授权的操作 |
| 通用执行器 | 一项能力覆盖大量任务，可用代码组合多步操作 | 权限面大，生成代码可能越界、死循环或耗尽资源 | 沙盒内计算、数据处理、临时自动化 |
| Skill | 文档易写易改，用到时再读取，维护成本低 | 自然语言和命令行转义容易出错，约束弱于 schema | 流程经常变化、参数简单、需要人类共同维护的操作手册 |

“能力做成什么形态”和“一次向模型暴露多少能力”是两个独立问题。即使全部使用专用工具，也可以只先展示索引、再按需加载 schema；即使使用 Skill，规模很大时仍然需要检索和分层组织。

默认可以优先考虑通用执行器，但安全、权限、审计或复杂参数一旦成为核心要求，就应该退回专用工具。复杂输入若仍通过 Skill 调用，可以先把结构化参数写成 JSON 文件，再由命令读取，减少引号与跨平台转义错误。

### 4. 好的工具描述首先说明“什么时候用”和“什么时候不能用”

工具描述不是接口名字的重复解释，而是帮助模型做决策的说明书。至少应写清：

- 适用场景与触发条件；
- 不适用场景、能力边界和反例；
- 每个参数的含义、格式、单位和具体示例；
- 返回结构、错误状态与可能产生的副作用；
- 大致延迟、费用或是否需要人工批准。

例如，“搜索文件”必须区分按文件名搜索和按文件内容搜索；“时间戳”不应只写 RFC3339，而应给出完整示例；“运行实验”必须说明工作目录、配置路径和输出目录。Agent 频繁选错工具时，应先检查描述是否含糊，再判断是否需要更强模型。

工具还应保证**参数传递保真**。运行时不能悄悄替换引号、改写路径或注入额外参数；如果必须规范化输入，应在工具描述和返回值中明确说明。否则模型看到的内容和工具实际操作的内容不一致，Agent 很难仅靠重试诊断故障。

### 5. MCP 解决接入标准化，Skill Hub 解决流程知识的分发，但两者都不自动等于可信

MCP 将工具、资源和提示等能力通过统一协议暴露给不同 Agent，降低框架之间重复适配的成本。Skill Hub 更像可检索的操作手册集合，Agent 先发现目录条目，需要时再读取完整说明，并通过已有执行器完成任务。

~~~text
MCP Server：把“可调用能力”标准化
Skill Hub ：把“如何完成任务”按需提供
Agent     ：选择能力、组合步骤并解释结果
Runtime   ：执行权限、审批、隔离、日志和超时
~~~

接入标准只解决“如何连接”，不解决“是否应该信任”。第三方 MCP Server、Skill 文档、网页和工具输出都可能包含错误或恶意内容。安装前应审查来源与权限；运行时采用最小权限、参数校验和敏感动作确认；执行后保留调用记录和实际产物。

### 6. 工具太多时，问题不只是 token 多，还包括选择干扰

把全部工具 schema 一次性放入上下文会带来三类成本：工具说明占用 token，模型要在大量相似选项中决策，某些工具还可能因名称或描述相近而被误选。

常见组织方式如下：

| 策略 | 做法 | 优点 | 风险 |
| --- | --- | --- | --- |
| 全量注入 | 一次展示全部工具 | 简单，不会因检索漏掉工具 | schema 成本高，选择空间大 |
| 静态预筛选 | 任务开始时检索一次候选工具 | 显著减少初始暴露量 | 首次检索漏掉后，后续难以补救 |
| 层次化目录 | 先展示类别或摘要，再展开具体工具 | 结构清晰，可控制上下文 | 分类错误会限制后续选择 |
| 主动工具发现 | Agent 在运行中调用发现工具，按需补充 schema | 能随着任务进展重新搜索 | 多出发现步骤、调用开销和停止判断 |

主动发现的价值要分开评价：它可能降低工具 schema 的注入量，但不必然提高任务准确率。W3 本地离线实验使用启发式 mock 路由，因此可以验证 token 与工具暴露量变化，不能把任务完成率直接解释成真实 LLM 的工具选择能力。

### 7. 多模态 Agent 的三条路线，比较的是编排方式而不只是模型能力

处理图片、PDF、音频或视频时，有三种典型路线：

| 路线 | 数据如何进入推理 | 优点 | 主要局限 |
| --- | --- | --- | --- |
| 原生多模态 | 原始媒体直接交给多模态模型 | 信息链最短，保真度较高 | 模型、格式、费用和上下文限制明显 |
| 先提取为文本 | OCR、ASR 或文档解析后再交给文本模型 | 文本可缓存、检索、审计和复用 | 提取阶段可能丢掉布局、颜色和空间关系 |
| 工具化分析 | Agent 在需要时调用图像、表格或音频分析工具 | 可迭代补证据，组合更灵活 | 编排复杂、调用次数增加，容易重复分析 |

评估时要区分**抽取错误**和**理解错误**：如果柱状图数字在 OCR 阶段已抄错，后续回答失败不能只归因于推理。成本比较也必须固定任务量、追问数量、模型和输入；若某条路线额外回答了颜色问题或重复抽取，就不能把全部增量都归因于路线本身。

在 BCI 场景中，波形截图、时频图和混淆矩阵适合多模态读取，但关键数值最好同时保留机器可读表格。图像理解可以帮助浏览，不能替代对原始数组、指标文件和生成脚本的核验。

### 8. 执行工具的可靠性来自运行时护栏，而不是提示词承诺

执行工具会写文件、运行代码、访问网络或改变外部系统，错误代价远高于普通文本生成。安全设计应覆盖执行前、执行中和执行后：

~~~text
执行前：解析目标 → 校验参数与路径 → 评估风险 → 必要时请求批准
执行中：限制目录、网络、时间、内存和权限 → 捕获 stdout / stderr
执行后：返回退出码和产物路径 → 校验结果 → 保留日志 → 必要时回滚
~~~

工作区路径检查只能证明受检查的文件工具没有越界，不能自动推出 Shell、代码解释器和其他工具也受相同限制。进程返回 0 只能说明程序正常退出，不能证明业务需求满足。可靠验收需要额外检查文件内容、测试断言、哈希或指标范围。

人类审批也不是一句“请确认”就够了。审批信息应包含将要执行的准确动作、目标、影响范围和是否可恢复；未接入审批通道时，高风险操作应默认拒绝。可恢复写入、幂等操作和最小 diff 能降低失败后的恢复成本。

### 9. Coding Agent 的核心是“观察—修改—验证”的闭环

Coding Agent 并不是一次生成整份代码，而是在文件系统、搜索工具、编辑工具和终端之间循环：

~~~text
理解任务与验收条件
        ↓
搜索并读取相关文件
        ↓
运行测试，获得真实基线或错误
        ↓
做最小修改
        ↓
重新运行测试、静态检查或验收脚本
        ↓
失败则读取新证据并继续；通过后报告改动和限制
~~~

搜索工具负责缩小范围，读取工具提供局部上下文，编辑工具产生可审查的 diff，Shell 和测试把假设变成可验证结果。工具输出过长时应截断展示并保存完整日志；编辑失败时要重新读取当前文件，不能假设旧内容仍然有效。

W3 的 Coding Agent 实验中，Agent 遇到 PowerShell 不支持 `&&` 的真实失败后改用分号，又根据验收脚本的数值差异修正代码。这说明错误恢复不是隐藏异常，而是把错误输出转化成下一轮动作依据。最终成功仍由 Agent 之外的验收脚本和单元测试判定，而不是依据模型的收尾说明。

### 10. Harness 决定 Agent 能否把“会写代码”变成“可靠完成任务”

Coding Agent 的成熟度不只来自模型。软件工程已有的测试、类型系统、版本控制、lint、构建工具和包管理器，共同构成了强 Harness。

| Harness 组件 | 解决的问题 | 不应被误解为 |
| --- | --- | --- |
| 测试与验收脚本 | 明确成功条件，提供可重复反馈 | 证明所有未知输入都正确 |
| 类型检查与 lint | 提前发现结构、接口和风格问题 | 证明业务逻辑正确 |
| Git diff 与文件哈希 | 界定修改范围，便于审查与回滚 | 证明文件从未被读取 |
| 沙盒与权限控制 | 降低代码执行的影响范围 | 消除所有安全风险 |
| 轨迹和日志 | 回放 Agent 的观察、动作和失败 | 自动证明最终结论正确 |

开始任务前应先固定验收条件，避免 Agent 修改实现后再改变判定标准。验收代码、测试数据和待修改代码最好分离，关键检查由外部 Harness 在 Agent 结束后独立复跑。这样即使 Agent 错误地声称“已完成”，仍能由确定性检查识别。

故障恢复也应按类型设计：可重试的网络错误使用退避；上下文不足时重新读取；工具参数错误时根据 schema 修正；连续重复失败时停止并请求人工介入。无限重试不是恢复机制。

### 11. 代码是通用 Agent 的元能力，因为它能精确表达、执行和沉淀过程

第 5 章把代码能力扩展到编程任务之外的六个方向：

| 方向 | 代码承担的角色 | 典型例子 | 关键约束 |
| --- | --- | --- | --- |
| 思考工具 | 进行精确计算和约束求解 | 统计、符号计算、组合搜索 | 代码与输入都需核验 |
| 业务规则约束 | 无歧义执行规则 | 审批条件、状态机、额度检查 | 高风险规则不能只靠模型解释 |
| 多媒体生成 | 用程序组织内容与迭代修改 | PPT、图表、视频流水线 | 需要渲染检查和质量反馈 |
| 系统适配器 | 解析变化中的格式并连接旧系统 | 日志解析、数据转换、诊断脚本 | 要区分预期变化与上游故障 |
| 生成式 UI | 把澄清、数据或操作变成交互界面 | 动态表单、可视化、SQL artifact | 动态代码不能拥有越权数据凭证 |
| Agent 自举 | 修复或生成新的 Agent | doctor、自定义工具、新 Agent 模板 | 基于已验证范例，防止错误代际累积 |

代码的优势在于中间数据可以留在执行环境中，只把最终结构化结果返回上下文，减少模型反复搬运大量文本。同时，代码可测试、可版本化、可审查，能把一次成功操作沉淀为可复用能力。

但“能生成代码”不等于“可以任意执行代码”。动态生成的软件可能漏掉权限检查，因此最终权限边界应下沉到稳定的数据层、受控服务或沙盒中。应用层可以做预检查，底层仍必须保留不可绕过的裁决。

### 12. 对 EEG/BCI 实验 Agent 的迁移

| 层次 | 建议实现 | 关键约束 |
| --- | --- | --- |
| 感知层 | 读取数据卡、配置、日志、指标 JSON 和论文证据 | 返回来源路径、版本、单位与必要片段，不把整个目录塞进上下文 |
| 执行层 | 预处理、特征提取、训练、评估和指标汇总 | 固定环境、随机种子、数据划分与输出目录；限制可写路径和资源 |
| 协作层 | 将数据检查、训练运行、结果复核分成明确子任务 | 交接输入、预期输出、停止条件和证据位置，不只传自然语言总结 |
| Harness | 单元测试、数据泄漏检查、指标范围检查、跨被试协议核验 | 验收逻辑独立于生成代码，失败日志必须保留 |
| 工具组织 | 高频高风险操作做专用工具，探索性分析使用受限 Python，流程说明写成 Skill | 不因工具数量增加就全量暴露；记录发现与选择轨迹 |
| 结果沉淀 | 保存配置、命令、源码快照、环境版本、指标和文件 hash | “程序运行成功”与“科学结论成立”分开判断 |

本周自造的 `summarize_bci_results` 指标汇总工具体现了一个适合迁移的最小闭环：读取多个结果文件，先在同一被试内合并不同 seed，再计算被试间统计量，并保留来源文件和记录下标。它解决的是统计汇总与可追溯性，不能替代对 LOSO 划分、数据泄漏或指标定义的检查。

W3 的最终落点不是给 Agent 无限的工具权限，而是让它在受控范围内完成一条可核验的实验链：知道何时读取证据，知道何时调用代码，失败时保留真实错误，完成后返回产物路径，并由独立 Harness 判断结果是否满足预先规定的条件。
