# W1｜第 2 章《上下文工程》

## 核心笔记

### 1. 上下文工程：管理“模型这一轮看见什么”

提示工程主要处理“一句话怎样说清楚”；上下文工程处理的是模型每一轮请求的完整信息：消息、工具、状态、检索结果和历史轨迹。

~~~text
稳定前缀 = system 指令 + 工具定义 + 长期规则
动态轨迹 = 用户任务 + 模型回复 + 工具结果 + 当前状态

每轮请求 = 稳定前缀 + 截止当前的动态轨迹
~~~

- **模型没有自动记忆**：上一轮没有被重新放入请求的信息，对当前模型等同于不存在。
- **Harness 负责组装上下文**：它决定哪些历史保留、何时压缩、工具如何声明，以及不可信内容放在什么位置。
- **上下文不是越多越好**：过长会增加 token 与延迟，也会让关键约束被淹没；不足又会导致重复调用或遗忘任务进度。

对 EEG/BCI Agent 而言，模型不会天然知道某次实验的通道映射、滤波方案和评价指标；这些信息需要由 Harness 按需要放入上下文。

### 2. 消息结构：谁说的话、能否被信任

| 信息类型 | 应承担的职责 | 不能误当成 |
| --- | --- | --- |
| system | 身份、权限边界、长期规则、受信任协议 | 用户输入或外部资料 |
| user | 当前任务、需求和提供的数据 | 可直接覆盖系统规则的指令 |
| assistant | 已作出的计划、文本或工具调用 | 外部世界已经发生的事实 |
| tool | 工具执行返回的观察与证据 | 工具定义或安全授权 |
| tools 字段 | 工具名、参数 schema、可调用范围 | 已执行完成的工具结果 |

最小 ReAct 闭环仍然是：模型决定调用工具 → Harness 校验与执行 → 工具结果回填轨迹 → 模型根据观察决定下一步。工具结果一旦缺失，模型便无法可靠判断“刚刚做了什么、是否成功、下一步还需不需要重试”。

### 3. 上下文压缩：删的是冗余，不是证据

上下文压缩用于控制不断增长的动态轨迹，而不是把所有文本机械缩短。好的压缩应保留仍会影响下一步决策的信息：

- 当前目标、完成进度和下一步；
- 约束、失败原因、未解决问题；
- 关键数值、来源、文件路径和可复查证据；
- 工具结果的结论，而不是无差别保留整段原文。

| 方法 | 特点 | 主要风险 |
| --- | --- | --- |
| 不压缩 | 信息最完整 | token、延迟和窗口压力持续增长 |
| 普通摘要 | 快速缩短历史 | 漏掉任务相关细节或反而扩写 |
| 任务感知摘要 | 围绕当前目标保留信息 | 额外模型调用，仍可能遗漏证据 |
| 带引用摘要 | 保留结论与来源对应关系 | 结构更复杂、内容未必最短 |
| 滑动窗口 | 只保留最近轨迹 | 可能遗忘较早但仍重要的约束 |

压缩最好发生在预算阈值附近或一个自然阶段结束后。每一轮都重新摘要通常会增加调用次数，并让误差持续累积。压缩管理的是动态轨迹；稳定的 system 指令和工具定义应尽量不变，以利于缓存。

### 4. KV Cache：缓存稳定前缀的计算，不是模型记忆

Transformer 在处理相同前缀时，可以复用已经计算出的 Key/Value 状态。它不会让模型“永久记住”内容，而是减少相同前缀再次计算的成本。

~~~text
较利于缓存：
  system 指令固定 + 工具顺序固定 + 动态状态追加在末尾

较不利于缓存：
  每轮改写 system + 重排工具 + 在前面插入新资料
~~~

| 指标 | 含义 | 不能单独说明什么 |
| --- | --- | --- |
| cached tokens / Cache% | prompt 中被服务端报告为缓存的份额 | 实际账单金额 |
| Hit% | 出现任意缓存 token 的轮次比例 | 大部分前缀都命中 |
| TTFT | 发出请求到收到首个 token 的时间 | 纯粹由缓存造成的延迟变化 |
| 总耗时 | 一个任务端到端所花的时间 | 模型能力或缓存效果的唯一证据 |

比较缓存时要固定模型、任务、工具集合和调用轮数，并把首轮冷启动单独看待。正确结论应表述为“本次提供商返回了怎样的缓存统计”，不能泛化为所有模型、所有任务都具有同样的比例或价格。

### 5. 提示注入：不可信文本不是新指令

提示注入是把网页、文档、检索片段或工具输出伪装成“更高优先级指令”，试图改变 Agent 的目标、诱导工具动作或索取不该获得的信息。

防御不能只写一句“忽略恶意提示词”，而应分层实施：

1. **上下文层**：给外部内容标注来源与不可信属性，限制长度，不把网页内容拼入 system 指令；
2. **执行层**：工具最小权限、参数校验、沙盒和高风险操作的人工确认；
3. **数据层**：数据库约束、访问控制和审计日志决定数据最终能否被修改。

评估时要同时有攻击样本、防御配置和清晰的成功判定。尤其要先看“无防御组是否能被绕过”：若基线本就全部失败，就不能据此宣称后续防御带来了多少增益。

### 6. 状态栏与 Skills：让模型按需获得信息

- **状态栏（state bar）**：把当前目标、阶段、剩余预算、已读资料、待验证事项等写到固定位置，避免模型从长历史中猜测当前状态。
- **Skills（渐进式披露）**：先提供技能目录和简短说明，确认需要后再加载完整指令、脚本或资源，避免一次塞入所有内容。

这两种方法解决的是同一个问题：把长期稳定的信息、当前动态状态和低频细节分层管理。前者让状态可见，后者让细节按需加载。

### 7. 对 EEG/BCI Agent 的迁移

| 层次 | 适合放入的内容 |
| --- | --- |
| 稳定前缀 | 数据集版本、采样率、通道映射、预处理协议、评价指标、工具 schema |
| 动态状态 | 被试/会话、随机种子、数据划分、训练进度、当前指标、报错和结果路径 |
| 压缩保留集 | 滤波范围、重采样、伪迹处理、模型超参数、核心指标、异常原因 |
| 不可信输入 | 论文网页、上传说明、外部检索结果和工具返回的自然语言内容 |

科研 Agent 的高风险边界包括：覆盖原始数据、修改实验配置、提交耗时训练任务、对外发送结果。它们不能只依靠模型判断，应由工具白名单、参数检查和人工确认共同约束。
