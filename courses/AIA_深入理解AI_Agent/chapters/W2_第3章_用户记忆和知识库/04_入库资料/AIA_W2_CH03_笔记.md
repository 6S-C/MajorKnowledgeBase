# W2｜第 3 章《用户记忆和知识库》

## 核心笔记

### 1. 持久化记忆不是“把对话塞得更长”

第二章管理的是一次任务内模型看见的上下文；本章管理的是任务结束后仍需被检索、更新和审查的知识。两者的共同点是都要把相关信息放回模型上下文，区别在于本章多了一条持久化的写入链路。

~~~text
原始对话 / 工具轨迹 / 文档          ← 可追溯证据，尽量只增不改
            ↓ 提取、标注来源和时间
用户长期记忆 / 共享知识库            ← 可审查、可更新的知识层
            ↓ 分块、索引、版本过滤
检索结果                              ← 仅在当前任务需要时进入上下文
            ↓
LLM 回答或提出下一次检索
~~~

- **用户记忆**服务于一个人：偏好、关键关系、历史事件与长期约束。
- **知识库**服务于一类任务或所有授权用户：论文、实验协议、数据字典、代码说明和结果文档。
- 模型回答中“提到过某事”不等于系统可靠地记住了它；可靠记忆必须能说明来源、时间、适用对象和当前是否仍有效。

对 BCI Agent 而言，受试者匿名编号、数据版本、预处理方案和历史结论都不能只靠聊天历史保存。原始实验日志、经审核的知识条目和运行时检索结果应分层保存。

### 2. 设计记忆时，先把“放哪里、怎么存、存什么”分开

| 维度 | 回答的问题 | 典型选择 | 设计提醒 |
| --- | --- | --- | --- |
| 存放层次 | 信息在什么时候可用？ | 当前轨迹、跨会话长期记忆、业务状态 | 当前上下文可压缩；审计用的原始轨迹不应被压缩结果替代 |
| 存储格式 | 信息用什么结构表示？ | Simple Notes、Enhanced Notes、JSON Cards、Advanced JSON Cards | 结构越丰富，更新和生成成本通常越高 |
| 记忆类型 | 信息描述的是什么？ | 情景、语义、程序记忆 | 一条信息可同时有多个维度，三套分类不能混为一谈 |

四种用户记忆格式不是“越高级越好”的排行榜：

| 格式 | 优点 | 主要短板 | 合适内容 |
| --- | --- | --- | --- |
| Simple Notes | 最轻、便于精确存取 | 上下文和关系容易被拆散 | 少量稳定事实 |
| Enhanced Notes | 保留一段完整叙事 | 冗余多，局部更新困难 | 与任务背景强相关的事件 |
| JSON Cards | 层级清楚，可局部改字段 | 预先设定的分类可能过于刚性 | 明确的用户画像字段 |
| Advanced JSON Cards | 额外记录人物、关系、来源背景和时间 | 写入与维护开销最高 | 需消歧、跨会话关联的关键事实 |

一个可用的最小原则是：**关键、少量、需要关系消歧的事实结构化保存；大量低频细节保留在可检索原始记录中。** 不要把模型猜测、一次性计划或未核对的敏感内容直接写成长期事实。

### 3. 记忆能力要按难度评估，而不是只看“能否答对一个事实”

本章将用户记忆评估成递进的三层：

1. **基础回忆**：能否准确找回用户明确说过的单条事实；
2. **多会话检索**：能否从不同时间、不同对象的多段会话中取齐信息，并在不充分时提出澄清；
3. **主动服务**：能否把看似分散的事实关联起来，先发现风险、再回查细节并给出有依据的建议。

第三层最容易被“看起来聪明”的回答误导。比如 Agent 看见旅行日期和护照到期日后主动提醒，必须同时验证：两条信息是否属于同一人、时间是否有效、原始对话是否真的支持该建议。评估要保留证据链，而不是只让另一个模型给总体印象分。

### 4. RAG 的核心不是“有向量库”，而是可检查的检索管道

典型 RAG 流程为：

~~~text
文档 → 清洗/分块 → 建索引
问题 → 稠密检索 + 稀疏检索 → 融合 →（可选）重排序
     → 证据片段 + 来源 → LLM 基于证据回答
~~~

**分块（chunking）**决定后面几乎所有环节的上限。块太小会丢失“这是谁、什么时候、哪个实验条件”的背景；块太大又会混入多个主题、稀释向量表示并浪费上下文。可从 256–1024 token、10%–20% 重叠作为起点，但最终应由同一批真实问题的召回证据决定。

RAG 的检索质量与最终回答质量也不是同一个指标：检索到正确片段只是给生成器创造了答对机会；若来源、上下文或提示边界处理不好，生成器仍可能遗漏限定条件或产生幻觉。

### 5. 稠密与稀疏检索互补：语义相似不等于精确命中

| 路线 | 它擅长什么 | 它为什么会漏 | W2 中应观察什么 |
| --- | --- | --- | --- |
| 稠密嵌入 | 同义改写、跨语言、表达方式不同但语义接近的文本 | 罕见代码、版本号、缩写和精确名称可能在向量空间中被弱化；分块也可能丢掉关键上下文 | 表示误差与 ANN 近似搜索误差要分开看 |
| BM25 稀疏检索 | 精确词项、编号、文件名、公式符号、错误码 | 不理解同义词和隐含语义 | 逐词 TF/IDF/BM25 贡献如何决定排序 |

ANN 进一步带来“搜索近似误差”：即使嵌入模型已经把正确文档表示得很好，索引也可能没找到真正最近的向量。实验 3-4 应把它和“向量本身没有表示出查询意图”的表示误差分开。

| ANN 索引 | 典型优势 | 典型代价 | 更像哪类 BCI 场景 |
| --- | --- | --- | --- |
| ANNOY（树） | 构建快、内存较低 | 不支持方便的增量写入，更新常需重建 | 版本固定的论文快照或已归档实验 |
| HNSW（图） | 召回通常更高、可增量插入 | 构建和内存开销更高，长期插入后仍需维护 | 持续新增的实验笔记与文献库 |

所以 W2 的问题“为什么语义检索会漏掉精确命中”至少有四个答案：嵌入表示、分块、近似索引和 top-k 截断都可能造成漏召回。BM25 不是落后方案，而是对精确符号检索的重要补偿。

### 6. 混合检索与重排序：把候选找全，再把顺序排对

混合检索先并行获得 dense 与 BM25 候选，再使用融合策略合成候选池。常用的 RRF（Reciprocal Rank Fusion）只使用各路名次：

~~~text
RRF(d) = Σ 1 / (k + rank_i(d))
~~~

它避免把余弦相似度和 BM25 分数直接相加。之后的重排序器以“查询 + 候选文档”成对深度比较，通常更准，但只应作用于较小的候选集，不能替代前面的召回与融合。

记录检索实验时至少区分：

- **hit@k / 简化口径的 recall@k**：正确证据是否进入前 k；
- **MRR**：第一个正确证据排得多靠前；
- **nDCG**：多个相关证据的整体排序是否合理；
- 延迟、索引大小、模型下载与失败样本。

如果一个问题有多篇相关文档，“前 k 中命中至少一篇”并不等于严格定义的 recall@k。实验记录要写清口径，避免把不同指标放在一起比较。

### 7. 更强的组织方式解决不同问题，知识更新要像改代码一样被审查

| 方法 | 擅长的问题 | 不应承担的任务 |
| --- | --- | --- |
| RAPTOR | 从总体概念逐步钻入细节 | 精确表达复杂实体关系 |
| GraphRAG | 多跳关系、实体消歧 | 无损保存条件、否定和时间依赖的自然语言 |
| 文件系统式知识库 | 人可读、可用 Git 版本化、按摘要逐层加载 | 只堆文件而不维护索引和双向链接 |
| 上下文感知检索 | 在索引期给孤立 chunk 补足来源/时间/实体背景 | 替代运行期的上下文压缩 |

知识更新应有三层：原始证据层、可修订的知识层、由已批准知识重建的索引层。新增证据不应直接覆盖主知识库，而应形成最小 diff，经独立审核、格式/链接检查和回放检索后再发布。对于冲突信息，先确认是否只是时间、对象或条件不同；证据不足时保留“待确认”，不要让模型强行选一个“最新答案”。

### 8. Agentic RAG 的价值在于“知道还缺什么证据”

Non-Agentic RAG 通常是一次检索后立即回答，适合边界清楚的简单问题。Agentic RAG 将检索变成工具，由 Agent 循环执行：

~~~text
分析问题 → 搜索证据 → 检查缺口 / 冲突 → 改写或分解查询 → 再搜索
                                                      ↓
                                        证据足够且满足停止条件 → 回答
~~~

- 多轮检索不是目的；每一次追加检索都应说明它要填补的证据缺口。
- 必须设置最大轮数、预算和停止条件，否则“继续查”会变成成本失控或重复查询。
- 检索到的网页、论文和工具输出是**不可信数据**，不是新的高优先级指令；应标明来源、限制其影响范围，并禁止它们直接触发删除、外发或提交任务等高风险动作。

本章的双层记忆是一个很实用的落点：少量 Advanced JSON Cards 提供随时可见的全局概览，原始对话或文档细节通过上下文感知 RAG 按需取回。只靠前者会丢细节，只靠后者又难以发现跨会话的隐藏关联。

### 9. 对 EEG/BCI 文献知识库的迁移

| 层次 | 建议保存的内容 | 关键约束 |
| --- | --- | --- |
| 原始证据 | 论文原文、数据卡、实验日志、命令输出、指标表 | 保留来源、版本、日期和文件 hash；不以摘要替代原始记录 |
| 结构化概览 | 数据集、采样率、通道集、预处理、划分、模型、指标与结论 | 每一项能回链到原始证据；冲突项显式标注 |
| 稠密索引 | 段落语义、方法描述、跨表述的相近工作 | 观察论文术语、缩写或参数是否被漏召回 |
| 稀疏索引 | 数据集版本、论文 DOI、通道名、频段、模型 checkpoint、错误码 | 保留精确 token 和符号，不做过度清洗 |
| Agentic 检索 | “某结论在何种被试/划分/指标下成立？”等需要多源核验的问题 | 查询轨迹和引用必须可复查；不把检索答案当临床建议 |

最小混合 RAG 的三道真实问题应由自己的 wiki 决定，并为每题人工指定“预期命中的证据文档”。例如：某数据集的采样率与通道数、某预处理组合对应的报告指标、某篇论文结论适用的被试划分。这样才能区分“回答写得流畅”与“证据确实被召回”。
