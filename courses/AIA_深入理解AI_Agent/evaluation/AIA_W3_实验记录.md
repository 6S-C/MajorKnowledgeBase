## 1. 2026-10-20｜实验 4-4：执行工具（10-23 有补充复核）

### 1.1 实验目的与方法

验证执行工具（execution-tools）的核心安全行为：工作区路径隔离、写入前语法校验、代码执行与真实返回状态、长输出截断落盘、危险命令在无审批能力时的 fail-safe 拒绝。实验运行于 `ai-agent-book-src\chapter4\execution-tools`，离线 demo，未连接 GitHub、日历、邮件等外部账户。本机已安装 Git Bash 但未加入 PATH，第二次运行时对当前进程临时加入。

### 1.2 实际结果

10-20 原始运行的输出摘要（见下方证据修正）：

| 步骤 | 结果 |
| --- | --- |
| `file_write` 写入词频统计脚本 | 成功，语法校验通过 |
| `file_edit` 搜索并替换脚本内容 | 成功，返回 diff 预览并通过校验 |
| 写入含语法错误的代码 | 被拦截，`Syntax validation failed` |
| `code_interpreter` 执行 Python 词频脚本 | 成功，`returncode=0`，输出 `{'BCI': 2, 'EEG': 1}` |
| 越界路径写入（`..\\outside_workspace.txt`） | 被拒绝，提示 outside workspace directory |
| 长输出处理 | 摘要记载：原始 1000 行中保留 102 行，完整输出写入临时文件；该临时文件未纳入本次归档 |
| 危险命令审批 | 无审批 API Key 时返回 `Command execution not approved`，未执行 |
| `virtual_terminal` 用 `wc -w` 校验 | 失败，`returncode=1`、无 stdout |

危险命令被拒绝是离线环境缺少审批模型时的 fail-safe 默认拒绝，不是在线模型评审了该命令。

10-23 补充复核（独立安全检查，真实落盘日志，属于 10-23 日期）：

- 代码执行：输出 42，`returncode=0`，`verification=passed`，`sandbox.kind=local-process`、`degraded=true`；
- 非法 Python 语法被本地语法校验拒绝；
- 工作区外目标路径被拒绝，未生成越界文件。

### 1.3 异常、处理与结论限制

- **证据完整性**：`4-4-execution-tools-run.log` 是当时输出的整理摘要，不是逐字捕获的原始控制台日志。10-23 的三个补充检查保存了实际 stdout/stderr；长输出截断与审批拒绝两项目前只有摘要留证，未重新执行。
- **Shell 失败原因不唯一**：demo 在设置临时 workspace 前已导入配置，文件实际写进了项目目录、而 Shell 检查的是声称的临时目录，仅这一初始化问题就足以造成"找不到文件"；缺旧 stderr，不能把失败唯一归因于 Git Bash 兼容。另外 `cli.py code --file` 的相对路径不按 workspace 解析，改用绝对路径后可进入执行器。
- 代码执行器报告的是本机进程级降级实现（local-process、degraded），不是容器隔离。路径拒绝验证的是文件工具的工作区检查，不能据此推断 Shell 或代码执行器也被限制在同一目录。
- 结论：语法校验、文件工具路径检查和代码执行已通过补充复核；无审批时默认拒绝的行为保留原摘要证据。完整 demo 仍有 Shell 失败步骤。

## 2. 2026-10-21｜实验 4-1：主动工具发现（离线 mock）

### 2.1 实验目的与方法

在同一个 126 个工具的本地工具库上，用同样的 8 个任务比较三种工具供给策略：全量注入（Full）、一次检索预筛选（Prefilter）、运行时主动发现（Discovery），观察工具说明 schema token 注入量、暴露工具数、调用次数和能力槽位覆盖。路由模型为脚本化启发式 `mock-offline`，工具嵌入用本地哈希词袋 `local-hash-512`（512 维）；参数 `top-k=4`、`prefilter-n=10`、`max-steps=10`；token 用 tiktoken `o200k_base` 计数。全程未调用任何 LLM 或 Embedding API，业务工具的执行结果同样返回 mock。首次运行前的分词词表缓存准备属于依赖下载，不是模型调用。

### 2.2 实际结果

| 策略 | mock 任务完成 | schema token 合计 | 平均暴露工具数 | 工具调用合计 | 平均策略耗时 |
| --- | --- | ---: | ---: | ---: | ---: |
| Full | 8/8 | 93,040 | 126 | 14 | 0.009 s |
| Prefilter | 4/8 | 8,236 | 10 | 10 | 0.007 s |
| Discovery | 8/8 | 7,796 | 10 | 28 | 0.012 s |

主动发现相对全量注入的 schema 注入量减少约 91.6%，降至原来的约 1/11.9；工具调用总数则翻倍，28 次中有 14 次 `discover_tools` 发现调用、14 次业务调用。Prefilter 在汇率+天气、加密货币+新闻、舆论查询、科研进展四个任务上漏掉了必需工具（如只调用天气、只调用新闻），一次 top-10 候选选择未能覆盖全部能力槽位。

### 2.3 异常、处理与结论限制

- 本结果只支持"按需加载能显著减少工具 schema 暴露"的机制结论；mock 路由器按已知关键词选工具，不模拟真实模型的指令遵循，8/8 不是 LLM 准确率。
- `injected_tokens` 只统计工具说明等指定 schema 文本，不是完整 API 请求 token，也没有计费数据；毫秒级本地延迟不含程序启动和索引初始化，不是线上延迟。
- 延迟来自单次本地运行，可能受分词器热身和系统调度影响，未做重复采样或运行顺序随机化，不据此判定哪种策略普遍更快。
- Full 与 Discovery 都是 8/8，本次没有观察到二者准确率差异；Prefilter 的失败同时受哈希检索表示与查询形式影响，不能推断所有预筛选方案都会失败。
- 论文下载、日历写入等业务工具均返回 mock，未访问真实外部服务。真实 LLM 的工具选择对照本周未运行。

## 3. 2026-10-22｜实验 4-3：多模态 Agent 三路线（10-23 复核发现成本归因问题）

### 3.1 实验目的与方法

对同一张样例柱状图和同一个中文收入问题，用同一个豆包视觉模型运行三种处理路线，观察答案正确性、信息保真、调用次数、token 与时延差异：① 原生多模态（图像直接进上下文，一次完成读图作答）；② 先抽取为文本再回答；③ 在②基础上挂载 `analyze_image` 工具的多轮对话。实际模型为 `doubao-seed-2-0-lite-260428`（项目别名 `doubao-1.6`，经 `ARK_MODEL` 解析），端点为 `https://ark.cn-beijing.volces.com/api/v3`。

样例为自动生成的 900×600 柱状图，各季度精确值可从柱顶标注直接读取。生成源码与渲染图片核对后，标准答案为 Q1/Q2/Q3/Q4 = 120/150/95/180 百万美元，最高 Q4。原版 demo 的运行窗口为 22:05:55–22:09:08，进程总耗时 193.02 s，退出码 0，stderr 为空。

### 3.2 实际结果

三条路线的收入最终回答均正确：四个季度数值、最高季度、单位全部与标准答案一致。原版 demo 未保存 usage，因此另做了计量复跑。下表采用成功复跑的同轮指标：首个 API 调用开始于 22:12:18，结果于 22:15:06 写入 JSON；两者界定的是计量轮次，不是原版 demo 的运行窗口。

| 路线 | API 调用数 | total_tokens | 同轮路线耗时 |
| --- | ---: | ---: | ---: |
| 1 原生多模态 | 1 | 1,702 | 10.458 s |
| 2 先抽文本再回答 | 2 | 4,176 | 49.832 s |
| 3 抽取+工具 | 6 | 12,773 | 109.275 s |

**表注：路线 3 的 6 次调用包含 demo 自动的颜色追问和一次被丢弃的重复抽取，工作量与前两条路线不同。此表是实际编排开销，不能据此推断公平条件下哪种路线必然更便宜。**

原版 demo 的三路线边界估时为 18.64 / 54.42 / 114.43 秒，由日志标题时间计算；这与上表属于不同轮次。两轮均为同一输入、同一模型的单次运行，未做多样本或重复统计。表中 token 为接口返回的总数，不是费用金额。

### 3.3 异常、处理与结论限制

10-23 复核确认了以下问题，均已在正文按复核口径处理：

- **共同依赖**：三路线共享同一个豆包视觉模型，这是编排对照，不是三种独立视觉能力；路线 2/3 的正确性首先依赖抽取把柱顶标签完整写进描述。
- **工具触发情况**：收入主问题未触发 `analyze_image`，颜色追问触发并验证了工具链路可用；只能限定为"本次主问题未用到工具"，不能概括为工具完全没价值。
- **重复抽取归因纠正**：被丢弃的多余抽取为 2,799 token，占路线 3 相对路线 2 增量约 32.6%；旧报告的 62% 把必需的第二次抽取也算进了冗余，不能沿用。必要的抽取不能全算浪费。
- **插桩事故**：第一次插桩为拿 usage 加了 `include_usage`，服务端返回空 `choices` 的纯 usage 帧触发 `IndexError`；第二次在辅助脚本过滤后成功。项目源码未改，但失败轮的完整 JSON 被成功轮覆盖，只余控制台摘要。
- **自动核验缺陷**：核验脚本会混入中间抽取文本，构造测试中错误的最终答案也能通过；本次最终答案经逐条人工阅读确认正确，自动报告不能当独立充分证据。
- **未完成项**：PDF 只生成保留，未跑原生 PDF/音频对照（相关路径硬编码 Gemini，本机无凭证）；计费金额与 TTFT 未记录。

## 4. 2026-10-23｜第 5 章：Coding Agent 编码闭环（主结果 run2）

### 4.1 实验目的与方法

用一个可独立判定的编码任务，观察仓库 `chapter5/coding-agent` 的 CodingAgent 在真实 DeepSeek API（模型 `deepseek-flash`，端点 `https://api.deepseek.com`）上能否走出“查看文件 → 运行失败 → 修改代码 → 重新验证”的闭环。Harness 准备初始错误文件和验收脚本，由仓库 Agent 修改代码，结束后再运行独立检查。

任务为修复 `accuracy` 的分母错误并加入空输入/长度不一致的 `ValueError`。运行前固定验收条件：`accuracy([0,0,1,1],[0,1,1,1])=0.75`（初始错误代码返回 0.6）；两类非法输入抛 `ValueError`；有覆盖五类场景的标准库 unittest 且通过；验收脚本与 `chapter5/coding-agent` 项目文件在运行期间不变。

### 4.2 实际结果

| 轮次 | 迭代 | 工具调用 | 进程耗时 | 验收 |
| --- | ---: | ---: | ---: | --- |
| run1 | 6 | 7 | 19.268 s | 最终代码通过；终端日志有编码噪声 |
| run2（主结果） | 8 | 8 | 24.750 s | 闭环完整可见 |

run2 的原始终端轨迹记录了闭环关键环节：LS → Read 两个文件 → Bash 用 `&&` 连接命令在 PowerShell 下真实失败（Agent 自行改用分号）→ 运行验收脚本得到真实报错（3/3 失败，0.6 ≠ 0.75）→ 两次 Write 修改 `metrics.py`、新增 `test_metrics.py` → 再调用 unittest → 收尾说明。四个阶段出现在同一条 stdout 中，但 CLI 截断了部分工具输入和测试输出；最终是否全部通过，以下面的独立验收日志为准。

Harness 独立复核（Agent 结束后另行执行）：

| 检查 | run1 | run2 |
| --- | --- | --- |
| 原验收脚本 | 3/3 通过 | 3/3 通过 |
| Agent 自写 unittest | 5/5 通过 | 5/5 通过 |

### 4.3 异常、处理与结论限制

- run1 的 `.pyc` 时间戳只能证明模块被加载，不能证明当时验收通过；其最终代码正确由后续独立验收证明。
- 应用层调用次数约 15 次（连通 1 + run1 6 + run2 8）只是顶层请求数推算，未落盘逐次 HTTP/账单证据，不写成已核实的精确付费请求数。
- Agent 两轮 token usage 未记录（当次流式请求未开启 usage 返回和收集），不估算补齐。
- "66 文件零变化"只覆盖 `chapter5/coding-agent`，且相对的是 DeepSeek 适配后的基线，不是整个仓库从未改动；文件哈希不变也不能证明文件未被读取。工具无容器或强制目录沙盒，"未越界"是未发生、不是被阻止。
- run1 的噪声来自 Windows 控制台代码页 936 与 UTF-8 命令不匹配；run2 把代码页设为 65001 后消除。Write 工具 lint 调用 `python3` 存根产生的假警告是本机环境现象，不是所有 Windows 必现。
- CLI 对工具输入输出有截断；退出码 0 与 "Completed" 不作为成功依据，判定完全依赖独立复跑。

## 5. 2026-10-25｜自造 BCI 实验指标汇总工具（排期自定义交付，无书中编号）

### 5.1 实验目的与方法

对应《十月排期》W3"把一条重复劳动做成工具，走 MCP 或直接函数注册"的自定义迁移实践。选择"读取多被试、多随机种子的本地实验指标 JSON 并汇总"作为目标，实现 `summarize_bci_results`：Python 标准库、零第三方依赖、本地运行、模型/API 调用为 0，通过本地 `ToolRegistry.dispatch` 直接函数注册调用。代码由编程助手按任务实现；本次验证的是工具交付与调用链路，不声称由自主 Agent 生成。统计口径：先对同一被试的各 seed 等权平均，再对被试等权平均，跨被试报告样本标准差（ddof=1，单被试返回 null）；按数据性质/数据集/模型/协议/split/session 分组，结果保留每条来源文件与记录下标。

### 5.2 实际结果

输入为**合成测试数据**（JSON 明确标记 `data_kind=synthetic`，4 条运行、3 个被试），不是真实 EEG 训练结果：

| 被试 | seed | accuracy | macro_f1 | kappa |
| --- | ---: | ---: | ---: | ---: |
| S01 | 1 | 0.7 | 0.6 | 0.4 |
| S01 | 2 | 0.9 | 0.8 | 0.6 |
| S02 | 1 | 0.6 | 0.5 | 0.2 |
| S03 | 1 | 0.7 | 0.6 | 0.3 |

| 指标 | 被试均值平均 | 被试间样本标准差 |
| --- | ---: | ---: |
| accuracy | 0.700000 | 0.100000 |
| macro_f1 | 0.600000 | 0.100000 |
| kappa | 0.333333 | 0.152753 |

（S01 先合并为 0.8/0.7/0.5；直接把 4 条 accuracy 平均会得到 0.725，与本工具的等被试口径不同。）

| 检查 | 状态/退出码 | 结果 |
| --- | --- | --- |
| 有效结果目录 | ok / 0 | 统计与手算一致 |
| accuracy 误填 85 | error / 2 | 拒绝，要求 [0,1] 比例 |
| 一条有效、一条缺 macro_f1 | partial / 1 | 用有效条目，报告缺失项，不把缺失当 0 |
| 请求 `..` 越界目录 | error / 2 | 拒绝，未读取外部文件 |
| 直接函数注册 dispatch 调用 | 成功 | 有效汇总与越界拒绝均实际跑通 |

单测 18 项：**17 项通过、1 项跳过**（跳过项为真实符号链接创建测试，本机系统不允许创建符号链接）。其中一项测试使用 50 组随机“被试×seed”布局，以独立手写均值/平方差公式核对通过；这 50 组已包含在上述单测中，不是额外 50 项测试。

### 5.3 异常、处理与结论限制

- 本次不是 MCP 服务实验，也未运行 LLM 自主选择工具；已走排期允许的直接函数注册路径。
- 样例全部为合成数据，数值不代表任何真实模型性能；真实结果 JSON 可不改核心工具直接汇总，但需先确认数据协议与指标单位。
- 工具只能验证输入格式与数值范围，无法判断上游数据泄漏、LOSO 划分是否正确等协议问题；读取根目录注册时固定，普通路径与解析后路径均做范围检查，但不是容器沙盒。

## 6. 本周个人总结与心得

这周学习第 4、5 章后，我对工具调用的理解更具体了。查看 Coding Agent 的 run2 轨迹时，可以沿着日志看到完整过程：模型先读文件，用 `&&` 连接命令失败后改用分号，再根据验收脚本中 0.6 与 0.75 不一致的报错修改代码，最后运行测试。对我来说，这把“调用模型”和“搭建智能体”的区别落到了实际操作上：模型负责决定下一步，工具负责执行，Harness 把结果交回模型；报错也是下一轮决策需要的信息。

主动工具发现实验让我进一步分清了机制验证与模型能力验证。Discovery 把工具说明量减少到 Full 的约 1/12，同时仍完成了全部 mock 任务，但这里的路由器按固定关键词工作，不能说明真实模型也会做出同样的选择。Prefilter 在本次设置下漏掉了四个任务需要的工具，这提醒我以后接入更多 BCI 工具时，既要检查说明量，也要检查必要工具是否进入候选集。只看省了多少 token，还不足以决定工具组织方式。

多模态实验中，三条路线都答对了同一张图，却没有直接给出哪种方式更好的结论。复核发现，路线 3 还回答了颜色追问，多做了一次被丢弃的抽取；旧材料又把不同轮次的 token 和耗时放在一起。整理这些证据后，我认识到比较成本前要先确认任务量与统计口径一致。以后比较 EEG 模型时，同样需要固定数据划分、输入长度和评价协议，不能只拿一列最终指标来判断改动是否有效。

这周另一个明确的收获是，验收需要独立于模型的收尾说明。Coding Agent 的程序正常退出，不能单独证明需求已经满足；而多模态自动核验器把中间抽取和最终回答混在一起，也可能漏掉错误。可靠的检查需要明确验收对象、预期答案和失败条件，再查看实际断言结果。后续做实验助手时，我会让它返回产物路径与检查结果，遇到失败保留原日志，而不是只保存一段“已完成”的总结。

自造 BCI 工具是在编程助手协助下完成的一次具体迁移。理解它的输入和输出时，我发现“汇总指标”首先要确定统计单位：同一被试多跑几个 seed，不应因此在等被试平均里获得更高权重。先被试内平均，再被试间平均，与直接平均全部运行会得到不同结果。工具将样例标成 synthetic，并保存来源文件和记录下标，也让我把上周“保留信息来源”的原则延伸到了实验统计中。下一步使用真实数据前，还需要核实协议标签和指标定义。

回看本周，已经完成的内容覆盖了工具执行、工具发现、多模态编排、编码闭环和本地工具交付，其中真实模型调用集中在多模态与 Coding Agent。后续优先补充主动发现的真实模型对照，以及多模态的等工作量比较；PDF、音频、MCP 和自造工具的 LLM 自主调用可按实际需要扩展。进入第 7 章评估时，我会继续关注固定验收条件、保存逐次证据和区分不同运行的统计口径，让结论能够回到具体文件与数据上核对。
