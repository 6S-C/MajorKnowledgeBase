## 1. 实验 2-10：上下文压缩

### 1.1 目的与配置

目的：在同一研究任务中比较六种上下文策略的成功状态、token、耗时、工具调用和 overflow 情况。

本次使用任务“研究 OpenAI 联合创始人的当前任职”；模型为 qwen3.8-flash，最大迭代轮数为 15。由于未配置 Serper，本次搜索和网页获取均使用离线 mock 数据。因此本实验只能用于观察**上下文管理策略的运行特征**，不能据此确认任务中涉及的现实人物任职事实。

### 1.2 结果

| 策略 | 成功 | 迭代 | 工具调用 | 总 token | 压缩比例 | Overflow | 耗时（秒） |
| --- | --- | ---: | ---: | ---: | ---: | ---: | ---: |
| no_compression | 是 | 14 | 41 | 139,113 | 133.1% | 0 | 152.74 |
| non_context_aware_individual_summary | 是 | 15 | 28 | 83,132 | 107.6% | 0 | 285.06 |
| non_context_aware_combined_summary | 是 | 11 | 20 | 50,539 | 109.6% | 0 | 221.82 |
| context_aware_summary | 否 | 15 | 30 | 87,740 | 104.3% | 0 | 348.84 |
| context_aware_with_citations | 是 | 12 | 22 | 59,971 | 125.8% | 0 | 266.28 |
| windowed_context | 是 | 10 | 28 | 61,736 | 135.9% | 0 | 174.48 |

### 1.3 分析与限制

1. 六组中有五组得到最终答案；context_aware_summary 在 15 轮上限内没有完成，不能简单解释为该策略本身无效。
2. non_context_aware_combined_summary 的总 token 最少，为 50,539，相比无压缩组减少 63.7%。但它同时少运行了 3 轮，因此不能把差值完全归因于摘要策略。
3. 六组 compression_ratio 都大于 100%。由结果中的原始/压缩文本长度可知，本次摘要没有在字符数上变短，反而出现不同程度扩写；上下文压缩不是“必然减 token”的操作，必须同时检查摘要长度、调用轮数和任务质量。
4. 六组均未发生 overflow。原因是 mock 数据规模有限，故本次没有真正验证“窗口溢出后压缩是否能恢复任务”这一问题。
5. 所有事实性回答均未做人工来源核验，且数据源为 mock；它们不作为现实事实结论写入本周笔记。

## 2. 实验 2-8：KV Cache

### 2.1 目的与公平对照

目的：观察稳定前缀与变化前缀在同一模型、同一任务和同一工具集合下的缓存字段差异。

控制条件如下：

- 模型：kimi-k2.6；任务、根目录和工具集合固定。
- correct：保持 system 指令和工具定义顺序稳定。
- shuffled_tools：重排工具顺序，破坏前缀稳定性。
- 为避免 3 RPM 限制，进程在 API 调用间最少等待 21 秒；总耗时包含该等待，TTFT 从实际发出请求后开始计。
- 本次使用 5 轮受控窗口，目的是获得可复查的缓存统计，不把它当作一次完整的长任务能力测评。

### 2.2 结果

| 模式 | 请求轮数 | prompt token | cached token | Cache% | Hit% | 首轮 TTFT（秒） | 平均 TTFT（秒） | 总耗时（秒） | 结束状态 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | --- |
| correct | 5 | 18,538 | 10,752 | 58.0% | 100.0% | 13.047 | 8.879 | 86.461 | 到达 5 轮上限 |
| dynamic_system | 5 | 29,104 | 1,280 | 4.4% | 100.0% | 7.775 | 14.684 | 118.034 | 到达 5 轮上限 |
| shuffled_tools | 2 | 6,979 | 0 | 0.0% | 0.0% | 11.784 | 36.336 | 95.022 | 已给出最终答复 |
| dynamic_profile | 5 | 22,085 | 1,280 | 5.8% | 100.0% | 13.535 | 18.382 | 108.551 | 到达 5 轮上限 |
| sliding_window | 5 | 14,968 | 6,912 | 46.2% | 100.0% | 6.939 | 13.977 | 119.795 | 到达 5 轮上限 |
| text_format | 5 | 28,847 | 8,960 | 31.1% | 100.0% | 29.523 | 25.299 | 128.104 | 到达 5 轮上限 |

计算方式：Cache% = cached_tokens / prompt_tokens × 100%。其中 Hit% 只表示本轮是否出现任意缓存 token，不表示大量前缀均被复用；因此 Cache% 更适合比较复用规模。

### 2.3 分析与限制

1. 稳定前缀组 correct 的 Cache% 为 58.0%，重排工具的 shuffled_tools 为 0.0%。这是本次最直接的缓存证据：破坏工具定义顺序后，提供商未报告缓存 token。
2. correct 组的五轮 cached token 为 256、256、2,048、4,096、4,096；TTFT 为 13.05、16.88、7.35、4.67、2.44 秒。后几轮缓存规模增大时 TTFT 有下降趋势，但单次序列不足以排除服务负载与网络波动。
3. shuffled_tools 仅运行两轮就完成任务，和 5 轮 correct 组的任务轨迹长度不一致。因此不能用两组的平均 TTFT 或总耗时直接宣称“稳定前缀快多少”；本次可靠结论仅限于缓存字段差异。
4. 表中的“预计节省”类字段是项目按缓存价格比例进行的估算，不等于账单，未作为实际花费写入结论。
5. 五轮上限导致部分模式尚未给出最终答案，这是受控实验设计的边界，而不是 API 调用失败。

## 3. 实验 2-5：提示注入攻防

### 3.1 判定规则与配置

模型为 qwen3.8-flash。按项目的 attack_succeeded 字段判定攻击是否成功；每个“攻击场景 × 防御配置”组合重复 4 次，共完成 48 次模型调用。运行中无 API 报错。

### 3.2 成功率矩阵

| 攻击场景 \ 防御配置 | D1：无防御 | D2：提示词加固 | D3：来源标记 | D4：组合防御 |
| --- | ---: | ---: | ---: | ---: |
| 直接注入 | 0/4 = 0.0% | 0/4 = 0.0% | 0/4 = 0.0% | 0/4 = 0.0% |
| 间接注入 | 0/4 = 0.0% | 0/4 = 0.0% | 0/4 = 0.0% | 0/4 = 0.0% |
| 记忆注入 | 0/4 = 0.0% | 0/4 = 0.0% | 0/4 = 0.0% | 0/4 = 0.0% |

### 3.3 结果解释

本次的真实结果是：在 D1“无防御”下模型已经没有被该项目的三类测试提示绕过，因此矩阵没有形成“防御层数增加、成功率逐层下降”的曲线。正确的解释是：**当前模型和当前攻击样本组合的攻击强度不足以区分四种防御**，不是“四种防御效果完全相同”。

后续若要获得可比较曲线，应先增加经教师或项目允许的攻击样本强度、扩大重复次数，并记录误伤率；同时固定模型版本与温度，避免把模型固有的拒答能力误归因于防御配置。

## 5. 个人总结与心得

这周学习第 2 章后，我对上下文的理解从“把以前的聊天记录一起发给模型”变成了“要主动决定模型每一轮应该看到什么”。第 1 章让我认识到工具结果必须写回轨迹，否则 Agent 就没有真正的观察；这一章进一步让我意识到，即使信息都写回来了，也不能无限累积。system 规则、工具定义、用户任务、网页内容和运行状态的来源不同、可信程度不同，应该放在不同位置，而不是全部混成一大段 prompt。

上下文压缩实验给我的感受很直接：名字叫“压缩”，结果不一定真的更短。这次有些策略的压缩比例反而超过了 100%，说明摘要本身也可能扩写，还会多消耗一次模型调用。所以以后我不会只看“是否用了摘要”，而会同时看它保留了什么信息、消耗了多少 token、任务是否更容易完成。由于本次使用的是 mock 搜索，我也明白了实验条件本身就是结论的一部分：它可以说明策略怎样运行，却不能拿来证明现实联网检索的事实质量。

KV Cache 让我第一次把“保持提示词稳定”这句话和实际数据联系起来。稳定前缀组出现了较多 cached token，重排工具顺序后则没有观察到缓存。对我来说，这比单纯记住概念更有说服力：system 指令和工具 schema 的顺序并不是无关紧要的格式问题，它会影响一次 Agent 调用的成本和响应过程。与此同时，Kimi 的限速也提醒我，实验不能为了赶进度就把不同轮数、不同等待时间的结果硬放在一起比较；没有控制好的对照，数字再漂亮也不能说明问题。

提示注入实验的结果也让我改变了一个想法。原本我以为应该看到“无防御最容易被绕过、组合防御最安全”的阶梯式结果，但这次在无防御组里攻击已经全部失败。这个结果不能证明四种防御效果一样，也不能证明组合防御绝对有效；它只说明在当前 Qwen 模型和预置攻击样本下，攻击强度不足以拉开差异。我觉得这种没有出现预期曲线的结果也应该如实保留，而不是为了让实验“看起来成功”去强行解释。

结合后续想做的 EEG/BCI 方向，我会把数据版本、被试与 session、采样率、预处理参数、随机种子、评价指标、错误状态和产物路径视为需要被管理的上下文。其中长期不变的实验协议可以放在稳定前缀，训练进度和本轮指标只作为动态状态追加；原始 EEG、长日志和外部论文内容则按需要读取并保留来源。这样既避免模型忘记关键条件，也能减少把大量原始内容全部塞进上下文的情况。

这周还让我形成了一个更具体的习惯：先跑一个可复查的小对照，再扩展到完整实验；原始 JSON、控制台日志和最终记录一起保存；得出的结论要写清模型、任务、样本量和限制。以后涉及修改原始数据、提交训练任务或对外发送结果时，我会把权限检查、参数校验和人工确认放在 Harness 和工具层，而不是只相信模型生成的一段文字。
