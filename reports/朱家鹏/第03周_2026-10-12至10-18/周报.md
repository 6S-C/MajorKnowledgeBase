## 💡 本周思考

**用户记忆和知识库检索解决的是同一个核心问题：从大量历史信息中选择当前真正有用的内容。**  
用户记忆面对的是长期积累的个人偏好与事实，知识库面对的是外部文档与证据。两者都不能简单地把全部内容塞进上下文，而要先判断什么值得保存、什么与当前问题相关、什么已经过时。通过本周实验，我把第 2 章的上下文工程与第 3 章连接起来：上下文工程负责组织模型当前可见的信息，记忆和检索负责在信息进入上下文之前进行筛选。

**检索方法没有统一的“更高级”，关键是它解决哪一类错误。**  
BM25 实验中，设备编号 `XK9-2B4-7Q1` 能准确排到第一位，而 `cat` 无法召回只包含 `kitten`、`feline` 的相关文档。这说明精确词面匹配对编号、错误码和姓名很可靠，短板主要是同义表达。知识库不应因为向量检索更新就完全丢弃 BM25，而应先判断问题需要精确匹配还是语义召回。

**稠密检索的错误要拆成“表示错误”和“搜索错误”。**  
ANN 实验只使用已有向量，测试索引能否找回真实近邻。HNSW 将 `ef_search` 从 20 提高到 200 后，Recall@10 从 0.557 提高到 0.992，平均查询时间从 0.026 ms 增至 0.121 ms。这个结果说明索引召回与查询开销存在直接交换关系，但它不能证明文本已经被正确编码。因此以后看到语义检索失败时，应分别检查嵌入模型和 ANN 参数，而不是只调一个 `top_k`。

**混合检索不会自动带来提升。**  
我原先认为把稀疏和稠密结果融合后会更稳，但个人轻量对照中 BM25 的 Recall@3 为 0.8333，LSA 为 0.7500，RRF 融合仍为 0.8333。弱稠密表示没有提供互补候选，反而可能把噪声带进排序。融合算法只能组合候选，不能凭空创造缺失的语义能力。

**Agentic RAG 的价值来自识别证据缺口。**  
简单问题中单次与分解检索的召回率都是 1.0；困难问题中分解检索把召回率从 0.5833 提高到 1.0，平均检索次数从 1.0 增至 1.5。多步检索适合一个答案需要多项事实的问题。它的停止条件应是“回答所需证据已经齐全”，而不是机械达到最大轮数。

**用户记忆必须用新会话验证。**  
真实 Kimi 实验将“物理量写明单位”和“代码优先 Python”提取为长期记忆，并在新会话回答中写出 `1 米 (m) = 100 厘米 (cm)` 和 Python 循环。这让我区分了当前上下文中的短期记住与跨会话长期记忆。稳定偏好适合长期保存，一次性问题应留在当前上下文；长期记忆还必须支持纠正、删除和来源追踪。

**本周的时间安排没有按计划执行。**  
排期把五组实验分散到五天，但实际代码运行集中在 10 月 18 日。虽然结果和记录已经补齐，但连续运行压缩了逐日思考时间，也不符合组长提出的实验分散要求。因此本周材料按实际日期记录，不倒填日期；下周应先固定每天一项实验的验收时间，当天完成“预期—结果—解释—边界”四项复盘。

**实验结论必须与证据等级一致。**  
本周同时包含真实 API 调用、本地算法运行和离线评测。如果只写“实验成功”，容易让不同证据被误认为同一强度。因此我在记录中分别注明：用户记忆使用 Kimi 真实调用，BM25 和 ANN 为本地算法对照，Agentic RAG 为预标注子查询下的离线比较。这样的标注虽然让结论显得更谨慎，但能保证每项判断都可以回到原始结果进行核对。

## 一、本周完成的工作

### （一）第 3 章学习：建立“记忆—检索—证据”框架

完成 1 份第三章学习笔记，结合教材正文、实验 README、源码入口和实际结果梳理 5 个主题。学习时没有只记录概念定义，而是为每种方法补充了适用问题、主要失败方式和判断依据：

| 主题 | 本周形成的认识 |
| :--- | :--- |
| 用户记忆 | 需要完成提取、保存、检索、使用、更新与删除闭环 |

| 稠密检索 | 适合同义改写，但要分开评估表示与 ANN 搜索 |

| Agentic RAG | 适合多事实问题，用证据缺口驱动下一次查询 |

经过整理，我形成了一条较清楚的工作链路：用户信息先经过记忆系统筛选和保存，知识库内容经过稀疏或稠密检索形成候选，必要时再融合、重排；当单次检索无法覆盖全部事实时，Agent 根据证据缺口继续查询，最后把经过筛选的记忆与证据送入当前上下文。

| Recall@5 | Precision@5 | MRR | 漏召回率 |
| ---: | ---: | ---: | ---: |
| 0.800 | 0.700 | 0.800 | 0.200 |

精确编号、HTTP 错误码和固定术语均成功命中；同义词查询 `cat` 未召回包含 `kitten`、`feline` 的文档，验证了词面不一致的短板。

我进一步查看逐词得分后发现，BM25 的优势不仅是运行速度快，还在于结果容易解释：可以明确看到查询中的哪个词为文档贡献了分数。对于实验日志、设备编号和报错信息，这种可解释性有助于快速判断“为什么召回了这篇文档”。

### （三）实验 3-4：ANN 索引对照

使用 3,000 个随机 128 维向量、100 条查询比较 Annoy 与 HNSW。

| 方法 | Recall@10 | 建索引 | 平均查询 |
| :--- | ---: | ---: | ---: |
| Annoy，`n_trees=10` | 0.173 | 17.5 ms | 0.021 ms |
| HNSW，`ef_search=20` | 0.557 | 179.0 ms | 0.026 ms |
| HNSW，`ef_search=200` | 0.992 | 219.6 ms | 0.121 ms |

本实验完成的是 ANN 搜索对照，不包含神经文本嵌入，因此没有写成完整语义检索复现。

本组对照也让我认识到，不能只比较单次查询耗时。Annoy 建索引快但本轮召回较低；HNSW 提高搜索范围后召回接近精确检索，但建索引与查询耗时同步增加。实际系统需要根据语料规模、更新频率和允许的漏召回率选择参数，而不是直接照搬最高召回设置。

### （四）实验 3-1/3-2：用户记忆真实调用

使用 Kimi `kimi-k2.6` 真实运行用户记忆流程：

运行过程中先后遇到模型温度限制、调用频率限制和 HTTP 解压库兼容问题。我分别检查服务端错误、调整模型兼容逻辑并更新依赖，最终得到可重复读取的 JSON 结果。这个过程说明，记忆实验不仅要检查模型回答，还要检查记忆文件中实际新增了什么，以及新会话是否真的加载并使用了这些内容。

### （五）实验 3-6：混合检索流水线

官方 BM25 阶段在 12 条查询上得到 Recall@3=0.8333、MRR=0.7917、nDCG@3=0.8026。个人编写 BM25 + LSA + RRF 的轻量对照：

| 方法 | Recall@3 | MRR |
| :--- | ---: | ---: |
| BM25 | 0.8333 | 0.8040 |
| LSA | 0.7500 | 0.6435 |
| RRF | 0.8333 | 0.8010 |

本周完成了官方 BM25 阶段和个人轻量混合对照。个人实现使用 LSA 构造稠密表示，再用 RRF 合并两路排序；它用于验证流水线和融合思路，不代替神经文本嵌入与重排器，后者作为后续扩展实验。

结果中 RRF 的 Recall@3 与 BM25 相同，MRR 还略低于 BM25。这一现象比“融合后提升”更有价值，因为它直接否定了我原先的简单假设：只有两路检索能提供互补且有效的候选时，融合才可能产生收益。

### （六）实验 3-8：Agentic RAG 离线对照

在 288 篇法律文档、21,372 个 chunk 和 7 条问题上比较一次性检索与分解检索。

| 难度 | 单次检索召回 | 分解检索召回 | 平均检索次数变化 |
| :--- | ---: | ---: | ---: |
| 简单题 | 1.0000 | 1.0000 | 1.0 → 1.0 |
| 困难题 | 0.5833 | 1.0000 | 1.0 → 1.5 |
| 总体 | 0.7619 | 1.0000 | 1.0 → 1.2857 |

本项子查询由离线数据预先提供，因此结论只覆盖检索策略，不包含在线模型自动规划、答案生成和 Token 成本。

多事实问题的检索轨迹表明，一次查询只找到了“过失致人重伤”相关法条，后续分别补查醉酒驾驶和累犯条件后，3 条目标证据才全部覆盖。这使“多步检索”从抽象概念变成了可观察过程：每一次新增查询都应对应一个明确的证据缺口。
